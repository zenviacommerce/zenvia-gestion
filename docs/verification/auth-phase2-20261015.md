# Auth Phase 2 verification

Run `npm ci && npm run build && npm test` with Node 22. Tests use jsdom, fake timers, real production tenant activation/authFetch/AuthScreen, and real supabase-js 2.105.0. Only the underlying global fetch is replaced. SDK method spies call through unchanged. Every unexpected network URL fails the test.

A: network password sign-in, exactly three requests at 0/500/1500ms; temporary classification and UI message, no credentials/reset message.
B: real production tenant bootstrap/getSession recovers a future-expiring session without network; localStorage is unchanged. This tests the startup Auth path, not rendering the entire application and its data screens.
C: 400 invalid_credentials, one request even after 30 seconds; no temporary message.
D: SDK refresh retries and AuthRetryableFetchError; saved session remains byte-for-byte unchanged.
E: stalled password requests abort at 6000/12500/19500ms; real AuthScreen warning at 18 seconds leaves login busy, session unchanged, then final temporary classification at 19.5 seconds.
F: HTTP 500 and 504 tested individually in password sign-in and refresh, including session conservation.
G: REST, Storage and Edge requests still pending after 60 seconds, original abort signal preserved, then complete successfully.

## Regression discovered

Before the fix, F/500 failed: `refreshSession()` returned AuthApiError and deleted the persisted session (expected JSON, received null). auth-js 2.105.0's NETWORK_ERROR_CODES includes 502/503/504 but not 500. Merely classifying the error in React is too late. authFetch now raises AuthRetryableFetchError for Auth HTTP 5xx so auth-js uses its recoverable transport-error path. The SDK wraps transport errors with status 0; the original HTTP status remains in the message. classifyAuthError explicitly recognizes AuthRetryableFetchError. No change to non-Auth responses, timeout or retry budgets.

The 19.5 second budget applies to password sign-in (three 6 second requests + 500ms/1000ms backoff). refreshSession has its own SDK retry budget (~30 seconds); tests advance 35 seconds to exhaust it and do not claim three refresh attempts.

Rollback: revert this branch's test/fix commit; nothing has been deployed or merged.

## Invalid refresh tokens

Additional real SDK tests cover HTTP 400 refresh_token_not_found and invalid_grant. Both emit SIGNED_OUT exactly once, remove the persisted session, leave getSession() null and make one network request even after 35 seconds. invalid_grant is classified as invalid-session only for HTTP 400. Local verification: 20/20 Vitest tests and production build pass.
