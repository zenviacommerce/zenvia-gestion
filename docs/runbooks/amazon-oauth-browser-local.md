# Disposable local OAuth browser harness

Status for this delivery: **prepared only; the real browser/Auth/Vault suite was not run**. Docker/local GoTrue and the Playwright Chromium engine are unavailable in the implementation environment. Syntax and guard checks do not establish a passing browser or database result.

`scripts/amazon-oauth-browser-local.mjs` runs a loopback HTTPS server around the actual `handleAmazonOAuthStart` and `handleAmazonOAuthCallback` functions. The reusable `local-auth-mfa-fixture.mjs` creates a real synthetic local GoTrue user, signs in and verifies TOTP. `local-oauth-provision.mjs` provisions that fixture's workspace, membership and subscription snapshot in the disposable local database. The handlers use real loopback Supabase Auth, REST, RPC and Vault-backed persistence, including the production trusted-human MFA RPC; no actor-context stub is substituted.

The server binds only `127.0.0.1:443` with a temporary one-day self-signed certificate generated by local OpenSSL. The default HTTPS port is deliberate: production OAuth configuration rejects nondefault ports. Use an environment that permits binding that loopback port and has no other listener there; do not loosen production URL validation. Playwright ignores the temporary certificate only in the two isolated test contexts. The server does not log incoming URLs, headers, bodies or raw errors.

## Prerequisites for a future authorized execution

Use a disposable Supabase local stack on `http://127.0.0.1:54321` or `http://localhost:54321`, with actual PostgreSQL 17, Vault, GoTrue MFA support and all app, MFA, OAuth and security-boundary migrations applied. Existing remote/production credentials or databases are prohibited. Install the repository-pinned Playwright package and its matching Chromium engine in that isolated environment through a separately approved setup step. This harness does not install a browser, start Docker, apply migrations or contact Amazon.

Supply these variables through the local runtime's environment without printing values:

| Variable | Requirement |
| --- | --- |
| `RUN_LOCAL_AUTH_VAULT_TESTS` | Exact `1` to permit fixture/browser imports and execution. |
| `ALLOW_DISPOSABLE_LOCAL_DB` | Exact `true` for the shared provisioning harness. |
| `LOCAL_SUPABASE_URL` | Exact loopback HTTP API origin on port 54321; no credentials, query or path. |
| `LOCAL_SUPABASE_ANON_KEY` | Disposable local anon/publishable key. |
| `LOCAL_SUPABASE_SERVICE_ROLE_KEY` | Disposable local service-role key. |
| `LOCAL_DATABASE_URL` | Disposable loopback PostgreSQL connection, required by the shared provider; never a remote database. |

Run `node scripts/amazon-oauth-browser-local.mjs` only after those prerequisites and authorization exist. Without the explicit execution flag, the command reports PREPARED ONLY and does not import Playwright, the fixture, handlers or Supabase clients. `node scripts/amazon-oauth-browser-local.mjs --check-guards` checks only URL/flag/key validation; it does not run Auth, Vault or a browser.

## Assertions and network boundaries

1. A real AAL2 fixture session POSTs start from the loopback UI origin. Actual Auth, entitlement and trusted-human MFA checks reserve the attempt through real RPCs.
2. Top-level ticket navigation receives the real Secure, HttpOnly, SameSite=Lax, Path=/ `__Host-zenvia-amazon-oauth` cookie. Playwright verifies its expiry and that the separate context has no binding cookie.
3. Playwright intercepts only the exact `https://sellercentral-europe.amazon.com/apps/authorize/consent` navigation and fulfills a local 303. It never continues that request to Amazon. Every other non-loopback browser request is aborted, and unexpected traffic fails the test.
4. Before releasing the legitimate redirect, a separate clean browser context visits the same signed state and simulated code. It must receive `failed` with zero LWA exchanges. The legitimate context must then receive `connected`.
5. The injected LWA dependency validates the exact token endpoint, form, simulated code and configured synthetic public pair, then returns a generated synthetic refresh token in memory. It never invokes network fetch for Amazon. The Supabase fetch wrapper permits only the guarded loopback API origin and rejects redirects.
6. A service-only coherent snapshot verifies the actual public app and simulated refresh token persisted through local Vault. The callback must expire the browser cookie. Replaying the callback must fail, with exactly one simulated exchange total.

On success the harness prints only non-sensitive booleans and the exchange count. It suppresses raw assertion and fixture errors. It always attempts browser, server, fixture/provider and temporary certificate cleanup, even if another cleanup fails. The provider removes only its synthetic attempt/account/Vault/workspace records, and the MFA fixture removes its sessions/user. Cleanup failures fail the harness. Never treat a prepared-only message, guard success, unavailable dependency or skipped execution as a passing HTTPS/MFA/Vault result.

## Prepared real database and Auth lifecycle runner

`node supabase/tests/amazon_oauth_local_supabase.mjs` uses the same explicit local flags, API keys and database variable. It invokes `psql` through loopback PG environment variables and stdin, never by putting the database URL or SQL in process arguments. Subprocess errors and secret payloads are not printed. The runner checks the installed PostgreSQL 17/MFA/OAuth contracts, races two independent claim connections, holds a callback transaction while a separate workspace-suspension connection waits on its row locks, checks old/new coherent snapshot tuples, injects a completion failure after real Vault update to verify rollback, and races a manual connection against the last OAuth quota slot.

The shared `local-oauth-lifecycle.mjs` then creates separate real GoTrue/TOTP fixtures for recovery authorization, global logout and Auth Admin factor removal. Each mutation is tested both before claim and after claim/before commit, asserting the prior private Vault token/version remain unchanged. These are prepared assertions, **not executed results** in this environment. An additional real-clock proof-expiry test requires `RUN_LOCAL_MFA_EXPIRY_WAIT=1`; it waits over five minutes for each of its claim and commit cases instead of falsifying Auth timestamps. The result explicitly reports whether those waits ran. An ordinary run without that opt-in does not verify real timed expiry.

The in-process PG17 tests use actual merged MFA/OAuth SQL with synthetic Auth relations/Vault and do cover stale original proof, membership/owner reassignment, expired sessions, missing AMR, recovery, factor changes and distinct member/owner workspace suspension. They complement the future GoTrue/independent-connection suite and do not replace it. Neither runner deploys or applies migrations; all fixture writes and cleanup require an explicitly disposable local stack.
