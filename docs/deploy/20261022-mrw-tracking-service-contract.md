# MRW TrackingService contract correction

Read-only WSDL/XSD retrieval on 2026-10-22 established the SOAP 1.1 operation `http://tempuri.org/ITrackingService/GetEnvios`, namespace `http://tempuri.org/`, and advertised SOAP endpoint `https://trackingservice.mrw.es/TrackingService.svc/TrackingServices`. The previously supplied `/TrackingServices/TrackingService.svc` path returned HTTP 404; the authoritative WSDL is available at `https://trackingservice.mrw.es/TrackingService.svc?wsdl`. Public contract snapshots are in `tests/fixtures/mrw-tracking-service/`.

The adapter uses the existing SAGEC `username` and `password`, with no separate tracking password or fallback override. Requests use language 3082, exact-number filter 0, the tracking number in `valorFiltroDesde`, empty `valorFiltroHasta`, empty date strings (both nullable optional strings in XSD), and information type 1. Optional subscriber/franchise fields follow the WSDL order. The builder can explicitly select information type 0 for bounded diagnostics. Credentials are XML-escaped, redirected requests are rejected, and the existing timeout/body limits remain in force.

Responses use namespace-independent local names and the nested `Seguimiento/Abonado/SeguimientoAbonado/Seguimiento` structure. Each movement requires an exact `NumAlbaran` match. Code `00` means delivered even with delivery attempts; positive attempts otherwise indicate an exception. Existing exact documented descriptions can normalize other states. Unknown states retain their sanitized numeric code or `UNKNOWN`, preserve previous reliable state, and record a fixed `MRW_UNKNOWN_STATUS_*` warning in health/state plus a console warning containing only provider and sanitized code. The observation itself is retained.

A timezone-qualified `Publicado` provides the event instant. Delivery-only fallback uses `FechaEntrega` ddMMyyyy plus `HoraEntrega` HHmm in Europe/Madrid. Invalid, nonexistent or ambiguous DST times remain undated. Shipment creation dates are not used as movement dates.

The adapter returns up to 200 matching history events in chronological order, with the newest movement separately selected. `reduceMovement` retains this history even when rejecting an older observation or protecting a terminal state. Persistence of this history is a separate additive SQL change owned by the release integrator. `PersonaEntrega`, `Referencia` and subscriber/account names never leave the parser.

Red/green evidence: the new contract suite initially failed all nine adapter/parser assertions; after implementation those passed. Worker warning and bounded-history assertions were separately observed failing before their implementation. Final targeted suite passes 11 assertions; Node adapter/policy/worker scripts pass 24 tests. No provider request with credentials, database operation or deployment was made during this implementation. The companion UI/probe/resume change updates the credential contract separately.

Review follow-up: the request builder accepts the existing SAGEC username aliases `userName` and `usuario` in addition to `username`. Both alias tests were observed failing before the fix. A dedicated worker regression verifies that an unknown earlier history event still records a sanitized warning when the newest movement is confirmed delivered. Targeted Vitest coverage now passes 14 tests; the Node scripts remain 24/24.

The release integrator's authenticated diagnostic then confirmed successful HTTP 200 responses and the following provider codes in actual exact-number/history results: `00` delivered, `16` out for delivery, `79` platform transit, `57` origin-franchise departure to platform, `17` collected at origin, and `47`/`48` awaiting collection. These seven codes now have provider-specific numeric mappings, tested with their Spanish history descriptions and independently of descriptions. Six new numeric-only assertions were observed failing before this mapping was added. No tracking numbers or credentials from that diagnostic are stored in fixtures.

The diagnostic also established that a two-number range can return multiple history events for both numbers. Future batching must group only explicit already-authorized tracking numbers by account and tenant, cap requested numbers and response size/history, filter every returned `NumAlbaran` against that explicit set, and persist each observation through its existing identity/lease guard. A numeric range must never discover or authorize new parcels. Noncontiguous numbers should continue as exact requests unless a bounded provider batch contract is separately verified. Current worker requests remain exact-number, sequential per account, with existing concurrency and pause limits.
