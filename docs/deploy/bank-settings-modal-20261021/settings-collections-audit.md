## Actual reusable primitives / style contracts

There is no generic `Modal`, `Section`, `Field`, `Button`, or `Badge` React export in `packages/ui/src/index.ts`. The names in the request map to these real contracts:

- **Modal:** `FormModal` in `packages/ui/src/forms/FormPrimitives.tsx`, re-exported through `src/components/forms/FormPrimitives.tsx` from `@zenvia/ui`. Props: open, eyebrow, title, subtitle, onClose, children, actions, className. Uses `.modalBackdrop > .modal.formModal.polishedModal`, shared header/close button/body/sticky actions. Concrete usage: `src/components/ProductModal.tsx` and `SupplierModal.tsx`. Source CSS is `packages/ui/src/forms.css`; local `src/shared-forms.css` only imports it. Width is min(760px, viewport minus32px), max-height min(88vh,900px); mobile <=700 becomes bottom sheet with one-column FormGrid. Note that FormModal itself currently lacks dialog role/aria-modal/label, Escape, and focus trapping. A bank editor should provide accessible dialog semantics locally and verify close behavior without broadly rewriting the package in this visual change.
- **Settings Section:** markup `.settingsSubsection`, `.settingsSubsectionHead`, h3, optional p in `src/pages/Settings.tsx`; source `src/settings.css`. Compare `GeneralSection` around lines303–314 (Documentos y aplicación). Border-top; padding18px22px desktop and16px <=760; h3 margin0 0 4px; final heading token `--ui-font-heading-sm` (15px). No heading icon in these subsections. Use this class for bank section and remove its independent margin/padding/icon styling.
- **Settings Field:** `label.settingsField > span + input/textarea/SelectField` (not a Field React component). Base grid gap7px; labels uppercase, weight800, tracking.045em; final label font token12px (`--ui-font-xs`), not the earlier base11px. Controls border token, radius10px, padding10px11px, body14px, minimum42px; teal focus border/ring. `settingsField>small` is muted12px helper text. Place optional marker inside the same span, with inline regular styling that does not become a separate grid item.
- **Settings Grid:** `.settingsFormGrid.settingsFormGridWide`: 3 equal minmax columns, gap15px, padding20px22px; <=1100 becomes2 columns, <=760 becomes1 column. Within `.settingsSubsection`, grid padding14px0 0. `.settingsFieldWide` spans2, reverting auto on mobile. Use this Settings grid within modal, with a scoped padding adjustment where needed; FormGrid is only2 columns and would not meet the requested3-column contract. Do not add gray FormSection/configEditor inset around bank fields.
- **Other reusable form components:** `FormSection`, `FormGrid`, `FormFieldSpan.full` are exported by @zenvia/ui. FormSection adds bordered padded card with optional icon; not the same appearance as Settings subsection, so do not substitute it blindly for this request.
- **Lists:** `.configList`, `.configRow`, `.configRowMain`, `.configRowActions`, `.configEmpty` in `src/sales-config.css`, used by TaxRegistrationsPanel and SeriesManagerModal. These are CSS primitives, not React list components. Row flex, min-width0, gap10px, padding11px12px, radius12px. Beware `.configRowMain` truncates strong/span/small with nowrap+ellipsis; grouped IBAN and actions must wrap on390px via scoped overrides. `.settingsRepeater`/`.settingsAliasList` exist but represent editable rows and use gray backgrounds. Integrations use list+separate editor as a positive behavioral reference.
- **Buttons/badges:** global native button classes `.primary`, `.secondary`, `.link`, `.iconBtn`, `.dangerIcon`, `.dangerText`, with readability/theme layers. Existing `.pill` / `.tag` are general status badge classes in `src/styles.css`, themed in `src/theme-consistency.css` and other theme layers; no Badge component. Prefer existing appropriate status treatment rather than bespoke `.bankAccountBadge` dimensions. Confirm normal/default pill color semantics with rendered peers before choosing modifier. Preserve text actions if they are clearer than icon-only controls.

## Banking changes to implement after Platform publication

1. `src/components/BusinessBankAccountsPanel.tsx` currently renders an unpadded standalone section with Building2 icon, list, and always-visible gray2-column `.bankAccountEditor`. Replace idle surface with standard Settings subsection, heading+description and `Añadir cuenta`, list/empty state only. Add button opens fresh draft; Edit opens hydrated draft. Keep alias, IBAN, BIC/SWIFT, holder and default checkbox; modal footer labels `Cancelar` / `Guardar`. No creation inputs in initial empty or populated state.
2. Reuse FormModal and Settings labels/grid. A local bank modal class can supply required grid/control geometry. Avoid a fixed editor and avoid gray inset FormSection. Remove unused Building2 import and obsolete editor CSS. Match title start/padding with Documentos y aplicación.
3. Keep existing save validation/service APIs, makeDefault, archive semantics and `zenvia:bank-accounts-changed` dispatch. Bank persistence is independent of General Save; `GeneralSection.reportDirty` merges generalDirty/bankDirty. Modal cancel/close must reset bank draft dirty only, never company dirty; successful save closes only after completion, errors remain visible in modal; failed validation should retain entered values. Block close while save is in flight or otherwise deliberately preserve asynchronous draft lifecycle.
4. Deletion already calls `confirmAction` in `remove()` and uses shared `ActionDialogHost` (`src/components/ActionDialogHost.tsx`), which is a real dialog with Cancelar/Eliminar, danger styling and historical-document explanation. Preserve this modal confirmation. If wording means confirmation inside account edit modal, do not silently remove global confirmation; select one concrete shared modal flow and test it. Never replace with window.confirm. General capture currently stubs confirmAction and does not mount ActionDialogHost, so it cannot prove rendered deletion confirmation.
5. Display IBAN grouped in blocks of4 in managed list and selector labels; retain normalized raw value for service payload/input hydration. Use a display-only helper shared between BusinessBankAccountsPanel and BankAccountSelect (potentially snapshots too). Do not normalize invalid legacy text into misleading groups: needs_review remains visibly correctable. Preserve BIC/holder and default/warning state.
6. `src/components/BankAccountSelect.tsx` is already the common selector for `InvoiceModal` (`src/pages/SalesInvoicesCore.tsx`, dates/payment section), `ReceiptModal` (`src/pages/SalesReceipts.tsx`), `OrderInvoiceModal` (`src/components/OrderInvoiceModal.tsx`, Shopify) and SeriesManagerModal. It wraps shared SelectField in `.bankAccountField` and currently outputs raw IBAN and a plain13px label. Prefer improving this single component/style so all selectors share appearance. SelectField is portalled with combobox/listbox roles, keyboard support and viewport positioning. Keep existing transfer-only visibility, series/global default fallback, manual override, unavailable selection warnings, and frozen snapshot behavior untouched. Be cautious adding settingsField globally: the document form label contracts differ; use shared bank style that matches peers in each context rather than imposing uppercase Settings labels on all sales fields.

Adjacent sales configuration deserves the same collection principle but is outside the Settings.tsx page: `TaxRegistrationsPanel` in `src/components/SalesConfigurationModals.tsx` always shows `.configEditor` next to list, nested in sales issuer-settings modal (`SalesInvoicesCore.tsx` around221). `SeriesManagerModal` in the same file combines list with permanently visible Nueva serie section. Flag for follow-up list+modal treatment; avoid conflating those nested modal decisions with bank styling. `TransportTariffsPanel` is an Orders transport import/review workspace, not an always-visible Settings collection creation form; detailed service/band editing is purposeful document review, so leave it out. Scalar global settings, toggle grids, preference-column checklists, maintenance diagnostic/repair tools and editable document line items are not independent Settings collection creation forms and should not be mechanically converted.

Suggested release boundary: deliver bank list/modal + selector visual consistency first, and explicitly account for the five Settings collection violations above in the authorized consistency work. If converting them in this release, preserve each distinct persistence boundary and validate separately; do not perform an indiscriminate global form replacement. No SQL, issued-document content, authentication/MFA or production-data migration is needed.
